# Research draft: Fyne lifecycle and Android background semantics for statistics checkpoints

Status: resolved research for ticket #4. Research date: 2026-11-27. No production code was changed.

Source policy: every external claim below is cited to a first-party source only: official Fyne documentation, the official `fyne-io/fyne` repository, official Android developer documentation, or AOSP source. Local claims are cited to `file:line` in this worktree. Claims are labelled **Verified** (directly stated or directly readable in cited source), **Inferred** (a code-level consequence, not an API contract), or **Recommendation** / **Decision question**.

Fyne version inspected: tag `v2.8.3`, whose changelog is dated 24 Nov 2026 at <https://github.com/fyne-io/fyne/blob/v2.8.3/CHANGELOG.md#L6> (raw: <https://raw.githubusercontent.com/fyne-io/fyne/v2.8.3/CHANGELOG.md>). Android documentation was read on 2026-11-27; AOSP line anchors are from `refs/heads/main` on that date and may move.

## Short answer

- **Verified:** current Fyne has `SetOnEnteredForeground(func())` and `SetOnExitedForeground(func())`, but there is **no** `SetOnEnteredBackground` method on `fyne.Lifecycle` or `fyne.App`. The background hook is `SetOnExitedForeground`. Sources: <https://docs.fyne.io/api/v2/fyne/lifecycle/>, <https://github.com/fyne-io/fyne/blob/v2.8.3/app.go#L158-L170>.
- **Verified:** on mobile, Fyne invokes both foreground and background hooks **inline** in the driver's single event loop; only `SetOnStopped` is queued. Sources: <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L195-L236>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L292-L329>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L372-L381>.
- **Inferred:** a synchronous checkpoint performed inside `SetOnExitedForeground` completes before the driver can dispatch a later foreground event; a checkpoint moved to a goroutine does not have that ordering.
- **Verified:** Android documents `onStop` (not `onPause`) as the place for heavier save work, and does not guarantee `onDestroy` before process death. Sources: <https://developer.android.com/guide/components/activities/activity-lifecycle#onPause>, <https://developer.android.com/guide/components/activities/activity-lifecycle#onStop>, <https://developer.android.com/reference/android/app/Activity#onDestroy()>.
- **Recommendation:** register `Lifecycle().SetOnExitedForeground` for a synchronous, idempotent statistics checkpoint; do not mutate or replace the in-memory `Session` on either background or foreground; do not restore round state after process death; keep cumulative CSV totals as the only cross-process state. The local checkpoint helper already exists at `internal/tui/practice.go:83-87`.

## 1. Verified facts: Fyne lifecycle API surface

1. **Verified:** `fyne.App` exposes lifecycle hooks through `Lifecycle() Lifecycle`, documented as "Lifecycle returns a type that allows apps to hook in to lifecycle events" and "Since: 2.1" (<https://github.com/fyne-io/fyne/blob/v2.8.3/app.go#L82-L85>; API page: <https://docs.fyne.io/api/v2/fyne/app/>).
2. **Verified:** the complete `fyne.Lifecycle` interface at tag `v2.8.3` is:
   - `SetOnEnteredForeground(func())` — "hooks into the app becoming foreground and gaining focus";
   - `SetOnExitedForeground(func())` — "hooks into the app losing input focus and going into the background";
   - `SetOnStarted(func())` — "app is now running";
   - `SetOnStopped(func())` — "app is no longer running".

   Source: <https://github.com/fyne-io/fyne/blob/v2.8.3/app.go#L158-L170>; identical text on the official API page <https://docs.fyne.io/api/v2/fyne/lifecycle/>.
3. **Verified:** there is no `SetOnEnteredBackground` identifier in `app.go`, `internal/app/lifecycle.go`, or the official API page. The internal implementation names the background callback field `onBackground` but exposes it as `SetOnExitedForeground`: <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/app/lifecycle.go#L11-L23>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/app/lifecycle.go#L30-L43>. The ticket's `SetOnEnteredBackground` name therefore does not match the current first-party API.
4. **Verified:** the internal implementation adds a nuance absent from the public interface comment: "Depending on the platform it may still be visible but will not receive keyboard events. On some systems hover or desktop mouse move events may still occur" (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/app/lifecycle.go#L35-L37>). Treat "background" as focus loss, not necessarily invisibility.
5. **Verified:** on mobile, `App.Quit()` is documented as doing nothing: "This function does no thing on a mobile device as the application lifecycle is managed by the operating system" (<https://github.com/fyne-io/fyne/blob/v2.8.3/app.go#L29-L36>). A stopped hook must not assume it was triggered by app-initiated quit.
6. **Verified:** Fyne's own preference system uses the stopped hook for an immediate save: the internal hook calls `prefs.forceImmediateSave()` after the user callback (<https://github.com/fyne-io/fyne/blob/v2.8.3/app/app.go#L176-L184>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/app/lifecycle.go#L67-L94>). This is precedent, not a general checkpoint guarantee.

## 2. Verified facts: Fyne mobile driver dispatch and event ordering

### 2.1 Stage model

- **Verified:** Fyne's mobile lifecycle stages are ordered `StageDead`, `StageAlive`, `StageVisible`, `StageFocused`; a transition crosses all intermediate stages, and `CrossOn` / `CrossOff` indicate direction. The source comment says `StageVisible` corresponds to Android `onStart` / `onStop`, and `StageFocused` corresponds to "onResume and onFreeze" (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/event/lifecycle/lifecycle.go#L7-L18>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/event/lifecycle/lifecycle.go#L87-L121>).
- **Verified:** `sendLifecycle(to)` drops duplicate stages, sends `lifecycle.Event{From: a.lifecycleStage, To: to, DrawContext: a.glctx}` into the app's event channel, then updates `lifecycleStage` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/app/app_darwin_and_unix.go#L18-L28>). The channel is an unbounded channel of `any` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/app/app.go#L62-L85>).

### 2.2 What Android actually feeds into that stage model

- **Verified:** Fyne's Android bridge registers native exports for `onCreate`, `onDestroy`, `onWindowFocusChanged`, `onNativeWindowCreated`, `onNativeWindowRedrawNeeded`, `onNativeWindowDestroyed`, `onInputQueueCreated`, `onInputQueueDestroyed`, `onContentRectChanged`, `onConfigurationChanged`, and `onLowMemory` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/app/android.go#L144-L216>). There is no `//export onPause` or `//export onStop` in that file.
- **Verified:** AOSP `NativeActivity` forwards Java `onPause()` and `onStop()` via `onPauseNative` / `onStopNative` to `ANativeActivity` callbacks (`callbacks.onPause`, `callbacks.onStop`), and forwards surface destruction via `onSurfaceDestroyedNative` to `callbacks.onNativeWindowDestroyed` (<https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/NativeActivity.java#203>, <https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/NativeActivity.java#230>, <https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/android_app_NativeActivity.cpp#469>, <https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/android_app_NativeActivity.cpp#483>, <https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/jni/android_app_NativeActivity.cpp#618>).
- **Verified:** Fyne's native loop sends `StageFocused` on `windowRedrawNeeded`, `StageAlive` on `windowDestroyed`, and `StageDead` on `activityDestroyed` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/app/android.go#L484-L517>). Because `StageAlive` is below `StageVisible` and `StageFocused`, the `StageFocused → StageAlive` transition crosses `StageFocused` **off**, which is what fires Fyne's background hook in code.
- **Inferred:** Fyne's background signal on Android is therefore tied to native window/surface destruction, not directly to `Activity.onPause()` or `Activity.onStop()`. The two normally correlate when an activity is covered, but the cited code does not establish a one-to-one mapping or a guarantee that the hook fires on every background transition. Fyne's own "onFreeze" comment names a callback that does not appear in AOSP `NativeActivity`; the implemented mapping above is the more reliable description.

### 2.3 Where callbacks run and in what order

- **Verified:** the mobile driver `Run()` calls `app.Main(...)`, inside which it calls `async.SetMainGoroutine()` and creates the queued-function channel (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L178-L187>). `app.Main` is documented as calling `f` on the App "in a separate goroutine, as some OS-specific libraries require being on 'the main thread'" (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/app/app.go#L11-L19>). The mobile driver package calls `runtime.LockOSThread()` in `init` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L66-L68>).
- **Verified:** the driver's single `for { select { ... } }` loop handles draw ticks, queued functions, and `a.Events()`; lifecycle events are passed directly to `d.handleLifecycle(e, current)` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L195-L236>).
- **Verified:** `handleLifecycle` calls the foreground hook directly on `StageFocused` `CrossOn`, and calls the background hook directly on `CrossOff` (after a final paint on Darwin/iOS). No goroutine and no `QueueEvent` is used for these two hooks (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L292-L329>).
- **Verified:** by contrast, `onStop()` queues the stopped hook with `l.QueueEvent(f)`; `fyneApp.Run()` starts `go a.lifecycle.RunEventQueue(a.driver.DoFromGoroutine)`; `RunEventQueue` drains the queue and invokes each function through the driver's `DoFromGoroutine(fn, true)` (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L372-L381>, <https://github.com/fyne-io/fyne/blob/v2.8.3/app/app.go#L74-L80>, <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/app/lifecycle.go#L101-L113>). Mobile `DoFromGoroutine` queues the function onto the same driver loop and, with `wait=true`, blocks until it has run (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/mobile/driver.go#L78-L105>).
- **Verified:** official Fyne docs state: "Since Fyne v2.6.0 all Fyne events and callbacks happen on the same goroutine"; Fyne APIs called from goroutines created by the app should use `fyne.Do`; `fyne.Do` may execute up to the next frame later, and `fyne.DoAndWait` waits for completion (<https://docs.fyne.io/started/goroutines/>). The same page states the model becomes default in v2.9.0 and requires `[Migrations] fyneDo = true` opt-in in v2.8; implementation: <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/build/build.go#L15-L29>, <https://github.com/fyne-io/fyne/blob/v2.8.3/thread.go#L1-L19>. Legacy `EnsureNotMain` moves a blocking `DoAndWait` call off main with a warning until migration is enabled (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/async/goroutine.go#L26-L44>).
- **Inferred (direct answer to the ordering question):** if the checkpoint runs synchronously inside `SetOnExitedForeground`, the driver cannot read any subsequent event — including a later `StageFocused` `CrossOn` event — until that callback returns, because `handleLifecycle` is invoked inline from the loop. Therefore foreground is delivered **after** the background save returns. This is a source-level consequence, not a documented Fyne API guarantee: the `select` may also service draw ticks or queued functions first, native producers may enqueue events from different threads, and `sendLifecycle` updates its stage field without synchronisation. If the save is started in a new goroutine instead, the callback returns immediately and the foreground event can be delivered **before** the save finishes.

## 3. Verified facts: Android lifecycle semantics relevant to a checkpoint

1. **Verified:** `onPause` is "the first indication that the user is leaving your activity" and the activity may still be visible in multi-window mode (<https://developer.android.com/guide/components/activities/activity-lifecycle#onPause>). The same guide states "`onPause` execution is very brief and does not necessarily offer enough time to perform save operations" and says not to use it to save application/user data, make network calls, or execute database transactions (<https://developer.android.com/guide/components/activities/activity-lifecycle#onPause>).
2. **Verified:** the `Activity` reference says "B will not be created until A's onPause() returns, so be sure to not do anything lengthy here" (<https://developer.android.com/reference/android/app/Activity#onPause()>). It also still says "you should use the `onPause()` method to write any persistent data (such as user edits) to storage" in its lifecycle-table notes (<https://developer.android.com/reference/android/app/Activity#ActivityLifecycle>). This conflicts with the newer guide in item 1; see decision question D5.
3. **Verified:** `onStop` is called "when your activity is no longer visible to the user", and the guide says to "use `onStop` to perform relatively CPU-intensive shutdown operations" with a database-save example (<https://developer.android.com/guide/components/activities/activity-lifecycle#onStop>). The same source says Home/Overview behaves "as if the current activity has been completely covered" (<https://developer.android.com/guide/components/activities/state-changes#activity-dialog-appears-in-foreground>).
4. **Verified:** "Starting with Honeycomb, an application is not in the killable state until its `onStop()` has returned"; the same source says under extreme memory pressure the system can kill the process at any time, and for methods marked killable "after that method returns the process hosting the activity may be killed ... without another line of its code being executed" (<https://developer.android.com/reference/android/app/Activity#ActivityLifecycle>).
5. **Verified:** "When the system kills an app, there is no guarantee that `onDestroy` is called in the app" (<https://developer.android.com/guide/components/activities/state-changes#process-kill>). The `Activity` reference says "do not count on this method being called as a place for saving data" (<https://developer.android.com/reference/android/app/Activity#onDestroy()>).
6. **Verified:** Android app process lifetime "isn't directly controlled by the application itself"; the system "can kill the process at any time to reclaim memory" (<https://developer.android.com/guide/topics/processes/process-lifecycle>). Cached processes "can be killed by the system at any time", apps should cease work in that state, and "Starting in Android 13, an app process may receive limited or no execution time until it enters one of the above active lifecycle states" (<https://developer.android.com/guide/topics/processes/process-lifecycle>).
7. **Verified:** lifecycle callbacks "always run in the UI thread of the process"; long UI-thread operations block all events including drawing (<https://developer.android.com/guide/components/processes-and-threads#Threads>). A 5-second input-event timeout is the ANR threshold cited in <https://developer.android.com/training/articles/perf-anr>.
8. **Verified:** `SharedPreferences.Editor.commit()` writes to persistent storage synchronously and returns success; `apply()` updates memory immediately, starts an asynchronous disk commit, and "you won't be notified of any failures". Pending `apply()` writes can block the main thread during lifecycle transitions and are a common ANR source (<https://developer.android.com/reference/android/content/SharedPreferences.Editor>).
9. **Verified:** saved state is not a statistics store: saved state bundles "persist through both configuration changes and process death but are limited by storage and speed", should not hold large data, and "Saved state APIs only save data written to it when the `Activity` is stopped" (<https://developer.android.com/topic/libraries/architecture/saving-states>). "Persistent local storage, such as a database or DataStore, will survive for as long as your application is installed on the user's device (unless the user clears the data for your app)" (<https://developer.android.com/topic/libraries/architecture/saving-states#local-storage>).
10. **Verified:** multi-window changes the meaning of pause: Android 10 (API 29)+ supports multi-resume where "all activities remain in the RESUMED state"; "`onStop()` ... is called any time an activity is taken off the screen" (<https://developer.android.com/guide/topics/ui/multi-window#lifecycle>). The activity guide likewise says an activity "might be fully visible even when it is in the Paused state" (<https://developer.android.com/guide/components/activities/activity-lifecycle#onResume>).
11. **Inferred / limitation:** the Android docs above constrain Java `Activity` callbacks, while Fyne delivers its hooks on Fyne's own main goroutine (section 2.3). Blocking inside a Fyne hook is therefore not literally blocking the Java UI thread, but it does block Fyne's event loop; no cited Android or Fyne source documents an ANR guarantee for work done in a Fyne callback.

Round state is explicitly in memory and not resumed on a later run (`docs/adr/0002-user-session.md:60-70`). Startup loads totals from CSV and starts a fresh session (`cmd/tui/main.go:114-141`).
- **Verified:** tests already cover coordinator checkpoint sequencing, save failures, idempotent merges, and preserved CSV bytes (`internal/tui/practice_test.go:24-53`, `internal/tui/practice_test.go:142-189`, `internal/history/store_test.go:144-191`, `internal/history/store_test.go:360-392`).

## 5. Recommendations: exact integration

R1. **Use the correct hook.** Register the checkpoint with `fyne.CurrentApp().Lifecycle().SetOnExitedForeground(...)`. Do not look for `SetOnEnteredBackground`; it is not in the first-party API (section 1). Treat `SetOnEnteredForeground` as a resume signal only: it should not save, reset, or restore anything.

R2. **Keep the checkpoint synchronous in the hook if durability is the priority.** Call the existing `practice.checkpoint()` helper (`internal/tui/practice.go:83-87`) — or a serializer that leads to it — directly inside the hook. This preserves the source-level ordering in section 2.3: a subsequent foreground callback is dispatched only after the save returns. Do not start a goroutine and assume the write finishes before backgrounding completes; Android explicitly allows process death after `onStop()` returns and says cached processes "can be killed by the system at any time" (<https://developer.android.com/reference/android/app/Activity#ActivityLifecycle>, <https://developer.android.com/guide/topics/processes/process-lifecycle>).

R3. **Do not clear or rebuild Practice state.** The hook must not call `quit()`, `start()`, or `repeat()`, and must not drop `practice.session`. If the process survives, the same in-memory `Session` continues on foreground; if it dies, a fresh process loads cumulative CSV via `history.Open` / `InitialStatistics` and starts a new session, matching `docs/adr/0002-user-session.md:62`. `SetOnStopped` should likewise not tear down the session, since Fyne fires it on mobile stage stop rather than guaranteed app exit (section 2.2).

R4. **Wire through one serialization point.** Fyne callbacks run on Fyne's main goroutine (section 2.3) while Bubble Tea's `Run()` owns its own loop (`internal/tui/model.go:31-35`), and `practice` fields are unsynchronised (`internal/tui/practice.go:7-11`). Expose a checkpoint entry point on the TUI adapter and either (a) add a mutex around `practice` state, or (b) send a checkpoint message into the Bubble Tea program and handle it in `Update`. Option (b) is simpler for data-race safety but gives up the "foreground after save returns" ordering in R2; this is decision question D1.

R5. **Use `SetOnStopped` only as a secondary, idempotent safety net.** If registered, point it at the same checkpoint helper. Fyne already queues this callback and runs internal preference saving after it (section 1, item 6; section 2.3), and the local `Store.Save` merge is idempotent (`internal/history/store.go:55-81`). Never rely on it as the primary background trigger.

R6. **Error policy.** Let `checkpoint()` retain the first save error in `practice.err` (`internal/tui/practice.go:83-87`), consistent with `docs/adr/0003-ui-and-color-scheme.md:62-73`. On mobile there is no visible terminal to report it; surface the error through the TUI on foreground or via a platform-appropriate notification path, and decide whether a failed background save should block resumed practice (D2). Do not silently discard the error or rewrite the CSV on a later no-op checkpoint.

R7. **Do not call `fyne.DoAndWait` from inside a lifecycle callback.** Fyne documents `DoAndWait` for goroutines created by the app (<https://github.com/fyne-io/fyne/blob/v2.8.3/thread.go#L1-L19>) and gates legacy behaviour on the `fyneDo` migration (<https://docs.fyne.io/started/goroutines/>). If a goroutine performs any follow-up UI work, marshal it with `fyne.Do`, not a blocking call from the callback.

R8. **Keep the save bounded.** The current write path validates, writes, syncs, and renames the whole CSV (`internal/history/csv.go:117-165`). That is a synchronous, blocking operation on whichever goroutine invokes it. Measure with realistic deck sizes before accepting R2; if too slow, decide explicitly between a partial async save and a smaller on-change checkpoint policy (D3).

R9. **Migration/build target.** Any Fyne-based build must add a Fyne dependency and set the `fyneDo` migration for v2.8 (`[Migrations] fyneDo = true`) per <https://docs.fyne.io/started/goroutines/> and <https://github.com/fyne-io/fyne/blob/v2.8.3/internal/build/build.go#L15-L29>, or target v2.9+ when its default applies. This is a new integration; nothing in the current worktree depends on Fyne (`go.mod:5-12`).

## 6. Limitations and decision questions

- **D1 — serialization vs ordering:** should the background checkpoint run inline on Fyne's goroutine (durable ordering, but race risk with Bubble Tea state) or be sent through the Bubble Tea program (race-safe, but foreground may be delivered first)? See R4 and section 2.3.
- **D2 — failure policy on mobile:** should a failed background save block resumed practice, as terminal save failures do today (`docs/adr/0003-ui-and-color-scheme.md:62-73`), or be surfaced non-blockingly?
- **D3 — save cost:** what is the largest realistic CSV, and is a synchronous temp-write + `Sync` + rename acceptable inside a lifecycle callback? The local implementation has no size bound (`internal/history/csv.go:117-165`); Android warns against lengthy main-thread work (<https://developer.android.com/guide/components/processes-and-threads#Threads>), and Fyne callbacks block its event loop (section 2.3).
- **D4 — hook coverage:** Fyne's Android background signal follows native window destruction, not Android `onPause` / `onStop` directly (section 2.2). Does the team accept this as the checkpoint trigger on Android, or require a first-party Fyne change/extra native hook? No cited source guarantees the hook fires on every process-kill path.
- **D5 — documentation conflict:** the `Activity` reference permits committing persistent data in `onPause` (<https://developer.android.com/reference/android/app/Activity#ActivityLifecycle>) while the current lifecycle guide forbids it (<https://developer.android.com/guide/components/activities/activity-lifecycle#onPause>). Recommendation R1-R2 avoids `onPause` entirely because Fyne does not expose it.
- **D6 — lock after process death:** the local store holds an OS file lock for the run (`internal/history/store.go:25-49`) and closes it via `defer` on normal exit (`cmd/tui/main.go:114-118`). No cited Fyne or Android source documents lock release after process death; verify on-device before relying on a restart after a kill.
- **D7 — rename durability:** local code `Sync()`s the temp file but does not `Sync()` its directory (`internal/history/csv.go:151-164`). No cited Fyne/Android source defines crash durability for that sequence; decide whether this matters for the statistics tolerance.
- **D8 — multi-window:** Fyne's background hook is documented as "losing input focus and going into the background" (<https://github.com/fyne-io/fyne/blob/v2.8.3/app.go#L164-L165>), and its desktop implementation explicitly tracks the app-wide current window (<https://github.com/fyne-io/fyne/blob/v2.8.3/internal/driver/glfw/window.go#L808-L838>), while Android 10+ can keep multiple activities RESUMED (<https://developer.android.com/guide/topics/ui/multi-window#lifecycle>). Decide whether a checkpoint on focus loss should also occur when another window takes focus but the app remains visible.
- **D9 — no automatic restoration:** keeping Practice in memory and starting fresh after death is a deliberate existing decision (`docs/adr/0002-user-session.md:62`). Confirm that "continue if process survives" means the same process keeps its `Session`, not that round position is serialized to disk.
